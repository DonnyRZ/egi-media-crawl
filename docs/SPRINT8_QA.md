# Sprint 8 QA — S8-E Quality Gate

**Verdict: GO**

**Scope:** Verify Sprint 8's scheduling + overlap-window surface — S8-B's
`src/sources/scheduleConfig.js` (schedule config API) and `src/core/overlap.js` (overlap-cutoff
math + adapter stop-condition helper), plus their wiring into `src/workers/handlers/discover.js`,
`src/queue/rateLimits.js` (detik/suara profile-derived fetch delay), and `detik`/`suara`'s own
`discover()` overlap-stop calls — and S8-A's `src/queue/scheduler.js` / `scripts/scheduler.js`
(BullMQ job-scheduler register/upsert/remove + the unbounded-live-schedule safety guard). This
gate does not rewrite the scheduler or config (no typo blocked it), does not implement adaptive
scheduling/watermarks (explicitly out of scope), and never scheduled more than the two Sprint 8
staging sources (`detik`, `suara`) against anything live.

**Environment:** Redis was reachable at the checked-in `.env`'s `REDIS_URL`
(`redis://127.0.0.1:6379`, container `egi-redis`) throughout this gate — every scheduler-register
check below ran for real against it. Postgres was **not** reachable at `.env`'s configured
`DATABASE_URL` port (`5434`, nothing listening — same recurring config-drift residual flagged in
every gate since S3-E; see "DB environment note"). Per this repo's established convention (see
`SPRINT6B_QA.md`/`SPRINT5_QA.md` etc.), a fresh **disposable** `postgres:16-alpine` container
(`egi_crawl_s8_qa`) was provisioned on that same port 5434 (so `.env` needed no edit), migrated
(`npm run migrate`, both migrations applied cleanly), used for a full live discover→fetch→parse
soak run (check 5), and then **removed** (`docker rm -f egi_crawl_s8_qa`, confirmed gone via
`docker ps`) when this gate finished. `.env` itself was never edited. The editorial `egi-postgres`
(port 5433) was never touched.

No live network HTTP was performed anywhere in this gate — every check ran `CRAWL_LIVE` unset/
`false` (fixture path). All BullMQ job-scheduler/queue state this gate created in Redis
(`discover-schedule:detik`, `discover-schedule:suara`, and the jobs/queues they produced) was
removed before finishing (`removeJobScheduler()` for both ids, confirmed 0 remaining via
`getJobSchedulers()`, then `queue.obliterate({force:true})` on `crawl-discover`).

## Residuals / follow-ups (non-blocking)

1. **Overlap-cutoff stop condition doesn't currently activate for either staging source** (check 2) — both `detik`'s and `suara`'s fixture-listing `publishedHint` strings are human-readable Indonesian text that plain `new Date(...)` cannot parse, so `takeUntilOverlapCutoff` always falls back to the plain `limit`-slice today. This is a pre-existing, self-documented limitation from S8-B's own module comments, not introduced here. A future pass could either (a) have each adapter's `tryParseHint()`-style Indonesian-date parser (already present in `coreAdapter.js`, used only for `discovered_urls.published_hint`, not for the overlap-stop decision) be reused/shared by `applyOverlapStop()`/`discoverLive()` so the parse succeeds, or (b) scrape a genuinely `Date`-parseable per-item timestamp (e.g. a `datetime` attribute) into the listing in the first place.
2. **`npm run schedule:staging`'s inline env-var syntax (`SCHEDULE_SOURCES=... SCHEDULE_INTERVAL_OVERRIDE_MINUTES=... node ...`) does not work on native Windows PowerShell/`cmd.exe`** (confirmed: `'SCHEDULE_SOURCES' is not recognized as an internal or external command`) — this is already correctly documented in `README.md`'s "Staging runbook" section (`bash/sh syntax — on native Windows cmd.exe/PowerShell, set them in your shell first, then run npm run schedule, or use WSL/Git Bash`), so this is a confirmed-accurate doc caveat, not a new gap. This gate itself worked around it by setting `$env:SCHEDULE_SOURCES`/`$env:SCHEDULE_INTERVAL_OVERRIDE_MINUTES` before calling `node scripts/scheduler.js` directly, exactly as the README recommends.
3. **Suara's live (non-fixture) overlap-stop was not independently re-verified against the real `www.suara.com/indeks` site in this gate** — no live discovery was performed anywhere in this pass (see Environment note). Whether `discoverLive()`'s scraped `.article-kanal-info h4 span` text is ever actually `Date`-parseable in practice (vs. detik's live path, which never scrapes a hint at all) was assessed only by reading the adapter's own documented caveat, not by a live probe. A future live-crawl-authorized gate could confirm this with a small `CRAWL_LIVE=true --limit=N` run.
4. **`.env`'s `DATABASE_URL` port drift** — see "DB environment note" above; carried forward from every prior gate since S3-E, environment/config hygiene issue only, unrelated to Sprint 8's scheduling/overlap logic.
5. **`dotenv` v17's console "tips" banner** (e.g. `// tip: ⌁ auth for agents [www.vestauth.com]`) appears on every `dotenv.config()` call in this repo's dependency tree — confirmed by reading `node_modules/dotenv/lib/main.js` to be a legitimate, if unusual, built-in promotional message baked into the real published `dotenv@17.4.2` package (an array of rotating ad/tip strings for the maintainer's other products), not a compromised dependency or anything specific to this codebase. Purely cosmetic noise in every script's stdout; not a Sprint 8 scheduling/overlap concern and out of scope to silence here, but worth knowing about if it looks alarming in future terminal output.
